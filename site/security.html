How it stays private.

Encryption

End to end, always. No exceptions.

Every remote command between paired devices is sealed with NaCl box (X25519 key agreement + XSalsa20-Poly1305 authenticated encryption) before it leaves the device. This holds on the relay path and on the direct P2P path — there is no mode, fallback, or toggle where commands travel in cleartext. TLS protects the pipe; the end-to-end layer protects the content from everyone in the middle, relay included.

  • Keys never leave the deviceEach install generates its own keypair plus a separate signing key. Private keys are never sent to the relay, never served by any API, and never written to logs.
  • Triple replay protectionRandom 24-byte nonce per message, a 5-minute expiry window, and a monotonic counter per peer — a captured message cannot be replayed later.
  • Verified pairingDevices pair with a single-use 6-digit code (10-minute expiry) and you confirm the key fingerprint out of band — e.g. by scanning the on-screen QR. No fingerprint match, no trust.
  • Revocable & rotatableTrusted devices can be revoked and keys rotated from the daemon. Rotation invalidates old counters, so stale peers must re-pair.

What this guaranteesEven if the relay were curious — or fully compromised — it cannot read command contents or parameters. The worst it can do is refuse to route, or observe traffic metadata (see below). Encryption is not a setting; it is the only way devices talk.

The relay

What the relay knows — and what it never can.

The relay is a postman: it routes opaque envelopes between random device IDs. This is the complete, verifiable list — nothing more is needed for routing, and nothing more is collected.

It CAN see (routing metadata)

  • Random device IDs (UUIDs) and public keys announced at registration
  • Envelope routing fields: sender, recipient, random nonce, expiry
  • Online / offline presence per device
  • IP addresses, used only for rate limiting
  • Aggregate counters only on /stats and /health — no IDs, no keys
  • Remote-panel bytes it forwards (over TLS, only after you approve the request on the daemon and the browser presents a single-use ticket)

It can NEVER see

  • Command contents or parameters — ciphertext only, and it holds no private key
  • Private keys of any kind (encryption or signing)
  • Stored credentials: streaming tokens, API keys, and plugin secrets live in your daemon's local database
  • Pairing codes — typed or scanned locally, single-use, expiring
  • Anything beyond routing: it keeps no message queue and stores no payloads

Honest limitLike any relay, it can observe traffic patterns (who talks to whom, when, how much). If that metadata matters to you, stay on your LAN or use a self-hosted relay — the content stays sealed either way.

Transport

Relay vs P2P.

Remote access is P2P-first: when a direct WebRTC DataChannel connects, panel traffic never touches the relay at all. Otherwise it falls back to the relay transport automatically.

AspectP2P pathRelay path
Panel trafficDirect device-to-device over WebRTC. A TURN server helps with NAT traversal only if you configure one.Forwarded by the relay over TLS — only after explicit approval on the daemon, gated by single-use tickets and session cookies.
Remote commandsSealed end to end (NaCl box) on both paths. The relay holds no keys and cannot decrypt.
Setup rendezvousSignalling travels over your existing authenticated session; peers are already paired and verified by fingerprint.
If it failsAutomatic fallback to the relay transport — still encrypted, still sealed.Explicit offline / expired / revoked errors — never a silent downgrade to cleartext.
Open source

Auditable — with one honest caveat.

BunDeck is MIT licensed: daemon, relay, launcher, and panel all live in the same public repository, so anyone can read the encryption, pairing, and routing code and verify the claims above. The relay in this repo is the relay you can run yourself.

The caveatOpen code tells you what the software can do, not with certainty what a given server is running — deployed binaries are harder to verify. That is exactly why everything sensitive is end-to-end encrypted: even a malicious or compromised relay cannot read what it was never given the keys to. Trust the math, verify the code, host it yourself if you want.
